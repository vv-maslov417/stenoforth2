# MT-синтаксис: краткая запись реальной многопоточности
SP-Forth 4.29, консольный `spf4p.exe` (`f:\spf429`); примеры — `devel\~stenoforth2-1\example`.
Проверено 2026-11-11.

---

## 1. Зачем

В примерах `example\parsum.f`, `example\mt-sum.f`, `example\mt-compile.f` одна и та же
многопоточная система каждый раз описывается заново: `VARIABLE` под флаг, `TASK:`, `START`,
цикл ожидания, ручная сборка результата. Смысл системы — 5–6 фактов, а кода — 40–60 строк.

Краткая запись сводит описание к строкам «одна директива — один факт»:

```
SHARED GO 0                       \ барьер старта
SHARED S1 0   SHARED S2 0         \ по ячейке результата на поток
SHARED D1 0   SHARED D2 0         \ флаги готовности
MUTEX  MX                         \ если есть общая запись
' B1 TASK: T1   ' B2 TASK: T2     \ тела потоков
: RUN 0 T1 SPAWN 0 T2 SPAWN 2DROP 1 GO ! JOIN-ALL ;
```

DSL не вводит новой семантики. Каждая директива — тонкая обёртка над тем, что уже есть
в SP-Forth и проверено в примерах: `TASK:` / `START`, `USER-VALUE`, `CreateMutexA`,
`EnterCriticalSection`, `WaitForSingleObject`, `SetThreadAffinityMask`.
Всё остальное — обычный Forth: `: ... ;`, локали `{ ... }`, `DO ... LOOP`.

Готовое ядро — файл `mt-dsl.f` рядом с этой справкой (листинг в приложении A).
Оно опирается только на `KERNEL32` и работает в обоих образах: `spf4p.exe` и `spf486.exe`.

Подключение:

```
S" f:\spf429\devel\~stenoforth2-1\example\mt-dsl.f" INCLUDED
```

Ядро лежит рядом со справкой, в `example\`. Путь держите ASCII: SP-Forth читает имена
файлов в кодировке системы, поэтому кириллицу в пути пришлось бы записывать в CP866,
а не в UTF-8.

## 2. Шпаргалка

| Строка | Что объявляет | Во что превращается |
|---|---|---|
| `SHARED S1 0` | общая ячейка с начальным значением | `CREATE , DOES>` (имя даёт адрес) |
| `TLS TV` | ячейка, своя у каждого потока | `USER-VALUE` |
| `MUTEX MX` | именованный мьютекс | `CreateMutexA(0 0 0)` → хэндл |
| `CRIT LOG` | критическая секция | `InitializeCriticalSection` (6 ячеек) |
| `MX LOCK` / `MX UNLOCK` | вход / выход | `WaitForSingleObject(INFINITE)` / `ReleaseMutex` |
| `['] INC MX WITH-LOCK` | слово под защитой | `LOCK xt CATCH UNLOCK THROW` |
| `LOG CRIT-ENTER` / `CRIT-LEAVE` | вход / выход в CS | `Enter/LeaveCriticalSection` |
| `['] LOG-WRITE LOG WITH-CRIT` | слово под CS | то же с CS |
| `' B1 TASK: T1` | задача по телу `B1` | `TASK:` (как в примерах) |
| `<x> <задача> SPAWN` | запуск с параметром `x` | `START` + запоминание tid |
| `tid JOIN` / `JOIN-ALL` | дождаться потока / всех | `WaitForSingleObject(INFINITE)` |
| `tid mask PIN` | привязать к ядру | `SetThreadAffinityMask` |
| `GO WAIT-GO` | ждать `GO=1` в теле | `BEGIN GO @ 0= WHILE 1 PAUSE REPEAT` |
| `tid SUSPEND` / `tid RESUME` | пауза / продолжение снаружи | `SuspendThread` / `ResumeThread` |
| `ms PAUSE` | пауза текущего потока | `Sleep` |

`SPAWN` оставляет tid на стеке — его можно сразу отдать в `JOIN` или `PIN`:
`0 T1 SPAWN 1 PIN`, `0 T1 SPAWN JOIN`.

## 3. Грамматика

Лексика: регистр не важен (Forth), имя — до пробела, значение — число или выражение,
комментарии `\ до конца строки` и `( ... )`.

```
spec    = { decl } .
decl    = data | guard | task | body | run .
data    = "SHARED" name value | "TLS" name .
guard   = "MUTEX" name | "CRIT" name .
task    = "'" entry "TASK:" name .
body    = ":" name { word } "TERMINATE" ";" .
run     = ":" name { run-word } [ "JOIN-ALL" | "JOIN" ] ";" .

use     = obj "LOCK" | obj "UNLOCK" | "[']" word obj "WITH-LOCK"
        | obj "CRIT-ENTER" | obj "CRIT-LEAVE" | "[']" word obj "WITH-CRIT"
        | value obj "SPAWN" | tid "JOIN" | go "WAIT-GO" | tid "PIN" mask .
```

Текстовая карточка для ТЗ и комментария в коде — те же пять фактов:

```
ПОТОКИ   T1:B1, T2:B2          (параметр START = 0)
ДАННЫЕ   общие: S1 S2 D1 D2 GO ; свои: TV
ЗАЩИТА   MX — общий счётчик CNT (+!)
СТАРТ    GO=1 после всех SPAWN
ФИНИШ    JOIN-ALL (или флаги D1&D2)
```

## 4. Директивы

### Данные

`SHARED <имя> <знач>` — общая ячейка. Имя возвращает **адрес**, как `VARIABLE`:
`S1 @`, `1 S1 !`, `1 CNT +!`. Значение задаётся в строке объявления, а не отдельным `!`.
Гонки не защищает: `+!` и пары «прочитал-изменил-записал» — только под `MUTEX`/`CRIT`.

`TLS <имя>` — ячейка, своя у каждой задачи: `42 TO TV`, затем `TV`. При старте потока
равна нулю (как все `USER`-переменные). Годится для индексов, счётчиков, состояния
тела; в примерах ту же роль играют локали `{ ... }`, а в образе stenoforth — `_`-локали.

### Защита

`MUTEX <имя>` — мьютекс: `CREATE` плюс `CreateMutexA(0 0 0)`, то есть **свободный**
(`bInitialOwner = 0`). Это важно: с флагом владельца (`1`) мьютекс отдаётся занятым,
и первый же `LOCK` из другого потока повисает навсегда (на этом тест завис, пока флаг
не сменён на нулевой).

`LOCK` / `UNLOCK` — вход и выход; `WITH-LOCK` выполняет слово и освобождает замок даже
при `THROW`:

```
: INC ( -- ) 1 CNT +! ;
: BUMP ( -- ) 10000 0 DO ['] INC MX WITH-LOCK LOOP TERMINATE ;
```

`CRIT` — критическая секция: `CREATE HERE 6 CELLS ALLOT` плюс
`InitializeCriticalSection` (6 ячеек — размер `CRITICAL_SECTION` на x86). Она дешевле
мьютекса, но не межпроцессная и без ожидания по времени. `WITH-CRIT` — то же, что
`WITH-LOCK`, для CS.

Никаких внешних библиотек: только `KERNEL32`, поэтому `mt-dsl.f` работает и в `spf4p.exe`,
и в `spf486.exe` (проверено в обоих).

### Потоки

`' <тело> TASK: <имя>` — штатное `TASK:` SP-Forth, ничего нового. Тело обязано быть
реентерабельным: только свой стек, свои локали, результат — в отдельную ячейку, признак —
в отдельный флаг. Завершать тело словом `TERMINATE`, как в `parsum.f`.

`<x> <задача> SPAWN` — `START` плюс запоминание tid. Возвращаемое `START` значение
проверяется: `0` означает, что поток не создался (и это `ABORT"`, а не тихий отказ).

`JOIN` / `JOIN-ALL` — ожидание по хэндлу потока, без опроса флагов: `WaitForSingleObject`
с `INFINITE`. Это надёжнее цикла `BEGIN D1 @ 0= WHILE 1 PAUSE REPEAT` и дешевле по CPU.
Флаги остаются нужны, когда ждут не завершения, а промежуточной готовности.

`PIN <tid> <mask>` — привязка к ядру. Из `parsum.f`: маска `1` — ядро 0, `4` — ядро 2;
соседние логические CPU одного физического ядра (SMT) выигрыша не дают.

`WAIT-GO` — барьер: тело стоит на нём, пока главный поток не выставит `1 GO !`.
Нужен, чтобы все потоки стартовали одновременно.

Штатные слова SP-Forth остаются в обороте: `ms PAUSE` — пауза текущего потока,
`tid SUSPEND` / `tid RESUME` — приостановка и продолжение снаружи, `tid STOP` —
аварийная остановка (`TerminateThread`, см. правило 8).

## 5. Шаблон системы

```
\ 1. данные
SHARED GO 0
SHARED S1 0    SHARED S2 0
TLS    TIDX

\ 2. защита (если есть общая запись)
MUTEX MX

\ 3. тела: реентерабельны, финал - TERMINATE
: B1 ( x -- ) DROP GO WAIT-GO  ARR HALF SUM S1 !  TERMINATE ;
: B2 ( x -- ) DROP GO WAIT-GO  ARR HALF + HALF SUM S2 !  TERMINATE ;

\ 4. задачи
' B1 TASK: T1
' B2 TASK: T2

\ 5. запуск и сборка
: RUN ( -- )
  0 GO !
  0 T1 SPAWN  0 T2 SPAWN  2DROP
  1 GO !
  JOIN-ALL ;
```

## 6. Примеры

### `parsum.f` в краткой записи

Было: `VARIABLE GO`, `WAITGO`, `TH1`/`TH2`/`TALL`, три `TASK:`, `ONE`/`TWO` с ручным
`PIN`, ожидание по флагам `D1`/`D2`. Стало:

```
SHARED GO 0   SHARED S1 0  SHARED S2 0  SHARED D1 0  SHARED D2 0
: TH1 ( x -- ) DROP GO WAIT-GO  ARR HALF REPS MASK1 RSUM S1 !  1 D1 !  TERMINATE ;
: TH2 ( x -- ) DROP GO WAIT-GO  ARR HALF + HALF REPS MASK2 RSUM S2 !  1 D2 !  TERMINATE ;
' TH1 TASK: TA    ' TH2 TASK: TB
: TWO ( -- ) 0 GO !
             0 TA SPAWN 1 PIN
             0 TB SPAWN 4 PIN
             1 GO ! JOIN-ALL ;
```

Ожидание по флагам заменено на `JOIN-ALL`, закрепление за ядрами осталось `PIN`.
Смысл тот же: два потока, половины массива, сумма в общей ячейке; ускорение на двух
ядрах — 1.78x, на SMT-соседях — нет.

### `mt-sum.f` в краткой записи

Блок задания из четырёх ячеек (`адрес`, `длина`, `сумма`, `флаг`) остаётся блоком —
это структура данных, а не примитив синхронизации. Краткая запись убирает только
обвязку запуска и ожидания:

```
CREATE JOB1 0 , 0 , 0 , 0 ,
CREATE JOB2 0 , 0 , 0 , 0 ,

: WORKER ( j -- ) { j | a n }
   j @ TO a   j CELL+ @ TO n
   a n SUM  j 2 CELLS + !
   1 j 3 CELLS + !   TERMINATE ;
' WORKER TASK: TASK1
' WORKER TASK: TASK2

: SUM2 ( a n -- s ) { a n | h }
  n 2/ TO h
  a h JOB1 JOB!
  a h + n h - JOB2 JOB!
  JOB1 TASK1 SPAWN DROP
  JOB2 TASK2 SPAWN DROP
  JOIN-ALL
  JOB1 2 CELLS + @  JOB2 2 CELLS + @ + ;
```

Проверено: `SUM2` на 2000 байтах даёт тот же результат, что однопоточный `SUM`.
Локали `{ ... }` свои у каждого потока — отдельные `TLS`-ячейки для этого не нужны.

Замечание про `mt-sum.f`: его локали с суффиксом `_` (`| xa_ xn_ |`, `V`, `-> x`) —
синтаксис образа stenoforth, поэтому файл штатно работает под `spf486.exe`, а в
`spf4p.exe` слово `|` не определено и файл на строке 42 падает с `#-2003`.

`spf486.exe` не принимает файл аргументом — он читает stdin, поэтому запускать так:

```
F:\spf429\devel\~stenoforth2-1\bin\spf486.exe
  S" f:\spf429\devel\~stenoforth2-1\example\mt-sum.f" INCLUDED
  MTS-DEMO
```

Проверено: `seq = 124716`, `par = 124716`, `half1 = 62286`, `half2 = 62430`, `OK`.

### `mt-compile.f` — отдельный класс

Это не про синхронизацию, а про **свой словарь у потока**: общий `DP` затирает код
соседа, поэтому каждому потоку даётся своё хранилище (`NEW-STORAGE` / `MOUNT` /
`DEFAULT-WORDLIST` / `SET-CURRENT`), а `thread-dp.f` даёт свою ячейку `DP` по `THREAD-ID`.
Краткая запись здесь не помогает и не мешает: `SHARED`-ячейки и `TASK:` те же, но
добавляется правило «компилировать только в своём хранилище».

## 7. Правила и ограничения (проверено)

1. **Реентерабельность.** Тело потока — слово без обращений к чужим локалям и без
   возврата результата на общий стек: результат в свою ячейку, готовность — в свой флаг.
2. **`+!` на общей ячейке не атомарно.** Тест 4×10000 под мьютексом дал ровно 40000;
   без мьютекса тоже 40000 — повезло, и это не гарантия. Общая запись — только под
   `MUTEX`/`CRIT`.
3. **Стеки.** Forth-стек каждого потока `_WNDPROC-CODE` размещает внутри стека
   OS-потока, поэтому задачи перезапускаемы. Но `HERE`/`ALLOT` общие: данные потока
   не выделять в словаре на лету.
4. **Компиляция в потоке.** Нужно своё хранилище: `NEW-STORAGE` — только в главном
   потоке (иначе `FORMAT` оставляет хранилище занятым и `MOUNT` падает с `#-2012`);
   монтировать базовое хранилище в задаче нельзя. `thread-dp.f` поддерживает до
   `DP-MAX = 16` потоков; при определённом `STORAGE-ID` он не патчит `DP`, и порядок
   загрузки — `storage.f` → `locals.f` → `thread-dp.f`.
5. **Локали.** `{ ... }` свои у каждого потока. `_`-локали (`xa_`, `V`, `-> x`) —
   синтаксис образа stenoforth (`spf486.exe`); в `spf4p.exe` их нет, и имя без суффикса
   не должно совпадать с системным словом (`jn_` зацикливает компилятор).
6. **Управляющие конструкции в режиме интерпретации** в задаче дают `#-312`: тело
   потока оформлять словом `: ... ;`, а не строками в консоли.
7. **`EVALUATE` в задаче работает** — входной буфер потоку не нужен.
8. **`STOP` — это `TerminateThread`.** Не снимает замки, не чистит ресурсы: только для
   аварий. Штатное завершение — флаг + `TERMINATE` + `JOIN`.
9. **`CreateMutexA` с `bInitialOwner = 1`** отдаёт занятый мьютекс: первый `LOCK` из
   другого потока повиснет. Создавать свободным (в `mt-dsl.f` — `0 0 0 CreateMutexA`).
10. **Аргументы `WINAPI:`** кладутся в обратном порядке C-прототипа: последний параметр
    C — глубже всех. Отсюда `SWAP` в `PIN` и `LOCK` (`( ms h )`, а не `( h ms )`).
11. **Потоки не ускоряют всё.** 1.78x на двух ядрах; при закреплении за SMT-соседями
    выигрыша нет (125 мс против 116 мс у одного потока).
12. **Кодировка.** Файл с BOM ломает первую строку (`п»ї...`); кириллица в путях и
    строках должна быть в CP866 — иначе «файл не найден» и `????`. Исходники и пути
    проще держать ASCII.

## 8. Чек-лист перед запуском

- [ ] Тело оформлено словом, завершается `TERMINATE`, не зависит от глобальных локалей.
- [ ] Результат — в свою ячейку; готовность — в свой флаг или в `JOIN`.
- [ ] Вся общая запись — под `MUTEX` или `CRIT`; мьютекс создан свободным.
- [ ] `SPAWN` возвращает не `0` (иначе поток не создался).
- [ ] После `1 GO !` есть `JOIN-ALL` или ожидание флагов — не «подождать и надеяться».
- [ ] Барьер открыт до `JOIN`: тело, стоящее на `WAIT-GO`, не даст `JOIN` завершиться.
- [ ] При закреплении за ядрами маски не указывают на SMT-соседей.
- [ ] Если тело что-то компилирует — у потока своё хранилище (`mt-compile.f`).
- [ ] Общий счётчик после прогона сверен с однопоточным эталоном.

## Приложение A. Ядро `mt-dsl.f`

Полный листинг — в файле `mt-dsl.f` рядом со справкой. Ключевые места:

```
: SHARED ( "name" init -- ) PARSE-NAME 2DUP CREATED PARSE-NAME EVALUATE , DOES> ;
: TLS    ( "name" -- ) USER-VALUE ;
: MUTEX ( "name" -- ) CREATE 0 0 0 CreateMutexA DUP 0= ABORT" MT: mutex" , DOES> @ ;
: LOCK   ( h -- ) INFINITE SWAP WaitForSingleObject DROP ;
: UNLOCK ( h -- ) ReleaseMutex DROP ;
: CRIT   ( "name" -- ) CREATE HERE 6 CELLS ALLOT DUP InitializeCriticalSection DROP DOES> ;
: WITH-LOCK { xt h -- } h LOCK xt CATCH h UNLOCK THROW ;
: SPAWN ( x task -- tid ) START DUP 0= ABORT" MT: thread not started" ... ;
: JOIN ( tid -- ) INFINITE SWAP WaitForSingleObject DROP ;
```

`WITH-LOCK` собран на локалях намеренно: вариант `SWAP >R LOCK R@ CATCH R> UNLOCK`
отдаёт в `UNLOCK` код возврата `CATCH` вместо хэндла — получается
`ERROR_INVALID_HANDLE` в каждом потоке (проверено).

## Приложение C. Что дальше

- `SEM`/`SIGNAL` — по образцу `~pinka\lib\multi\Semaphore.f` (`CreateSem`, `ReleaseSem`);
  нужны для ограничения параллелизма (пул из N исполнителей).
- `QUEUE` — `~ygrek\lib\multi\queue.f`, `msg.f` и `~yz\lib\channel.f`; DSL их не
  дублирует, а описывает владельца и защиту.
- `PARALLEL ... ;PARALLEL` с автоматическим `TASK:` по списку тел — следующий шаг,
  если понадобится запускать десятки однотипных задач без ручных `SPAWN`.
